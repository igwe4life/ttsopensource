# 100-language GPU pool — status and findings (2026-10-20)

Everything here was measured on RunPod during one session; nothing is running now.

## What exists

- `language-registry/pool-languages.json` — the 100 broadcast languages (48 Piper, 52 MMS, 26 African),
  ordered so round-robin sharding (entry *i* → pod *i % N*) gives every pod an even Piper/MMS mix.
  Regenerated by `node scripts/build-registry.js` (which calls `scripts/add-pool-languages.js`).
- `language-registry/pool-live.json` — the 47 MMS-only languages intended for the first pooled broadcast
  (es/fr/de stay on the original single-GPU stack, see "Known problems").
- gpu-service: startup preload (`PRELOAD_LANGUAGES`), on-demand Piper voice download, capped Piper CUDA
  arenas (`PIPER_GPU_MEM_MB`), bounded TTS thread pool (`TTS_WORKERS`), NLLB output cap, `uroman` for MMS,
  and `/health` fields `preload` and `models.tts_errors`.
- orchestrator: `GPU_POOL` (comma-separated gpu-service URLs; each chunk goes to every pod with its own
  language shard), `SOURCE_RELAY=true` (one shared pull of the source, re-served locally), in-process WAV
  resampling, staggered pusher start.
- `deploy/runpod/pool/*.cjs` — scripts that create/patch/poll/tear down the pods (credentials are read from
  `deploy/runpod/.env` at run time; set `POOL_FILE` to choose a language list and `STREAM_URL` for the source).

## Measured

| Setup | Result |
|---|---|
| RTX 3090, 25 languages/pod (13 MMS) | ~1.8–2.9 s GPU time per 4 s chunk |
| MMS TTS | ~0.1 s per language (the expensive path); Piper ~0.03 s |
| 2 pods × 50 languages | too slow for 4 s chunks (MMS-heavy shards 4–6 s) |
| 4 pods × 25 languages | wall ~2.9 s per chunk, within budget |
| Orchestrator, 16 vCPU CPU pod | 100 pushers ≈ 4 of 16 cores |
| 50 pushers (relay on) | clean 25 fps on sampled streams |
| 100 pushers (relay on) | all alive, but sampled streams only 13–20 fps |
| 100 pushers (direct pulls) | only 57 of 100 stayed up |

So the practical ceiling is ~50 simultaneous streams to `web.homestream.live` from one source. It is not the
GPUs. Cause not isolated (RTMP server vs. pod egress vs. relay); a read-from-disk relay was tried locally and hung.

## Known problems (deferred by the user)

1. **Piper in the pooled image**: for most Piper languages (including es/fr/de) synthesis fails *intermittently
   and per language/chunk* with `wave.Error: # channels not specified` (the voice produced zero audio chunks).
   Voices work alone via `/tts` with natural text; NLLB single-language translation is fine. It happens via the
   WebSocket path (`translate_many` → `translate_multi`), so the suspect is the batched translation returning
   empty/unusable text for some language+chunk combinations (or a Piper regression from this build). The
   production stack (older image) is unaffected — **do not move es/fr/de to the new image until fixed.**
   Next step: make failures include the text, and fall back to the single-language translate when a batched
   result is empty.
2. Piper voices for lt, th, he, ja need special phonemizers the installed piper-tts lacks; th/he use MMS,
   lt/ja were swapped for ilo/war.
3. MMS-TTS checkpoints are CC-BY-NC 4.0 (non-commercial).
4. 24 GB cards are enough for ~25 voices + Whisper + NLLB per pod (~15 GB free after preload).

## Cost reference

RTX 3090 $0.50/hr (RTX 4090 $0.89/hr was faster for MMS), 16 vCPU CPU pod $0.48/hr, A40 $0.59/hr.
